> 分析日期：2026-07-11

## 1. Value —— 价值假设

### V1: 独立开发者是否真正需要"Agent 操作引擎"？
- **假设**：手动在引擎里拖拽配置是独立开发者的核心痛点
- **置信度**：中（60%）
- **判断依据**：Game Jam 场景下时间压力明显，但日常开发中开发者可能已习惯 GUI 操作
- **验证实验**：访谈 10 位独立开发者，问"你上次在引擎里重复做超过 10 次的机械操作是什么时候？花了几分钟？"统计是否高频
- **如果失败**：缩小范围——不做全面的引擎操作 Agent，只做 3D 资产 Pipeline Agent（更容易量化价值）
- **风险等级**：橙色

### V2: AI 3D 模型质量是否满足独立游戏的"能用"门槛？
- **假设**：TRELLIS / TripoSR 等模型产出的 3D 模型在 Prototype 阶段足够用
- **置信度**：中高（75%）
- **判断依据**：TRELLIS CVPR 2025 已证明质量，但生成结果的一致性（多角度、风格统一）仍有差距
- **验证实验**：用 5 种不同风格 prompt（写实/低多边形/卡通/科幻/古风）各生成 10 个模型，让 3 位游戏美术打分（1-5），目标平均分 ≥ 3.5
- **如果失败**：AI 3D Pipeline 先聚焦到"低多边形 / 体素"风格（质量更可控），或只做模型检索+修改而非生成
- **风险等级**：橙色

### V3: 开发者是否愿意信任 Agent 对项目文件做写操作？
- **假设**：Agent 修改代码/场景的准确性足以被信任
- **置信度**：中（55%）
- **判断依据**：Claude Code 在通用项目中已有不错表现，但游戏工程（场景 YAML/二进制、Prefab 嵌套）远比文本文件复杂
- **验证实验**：构建 10 个典型游戏修改任务（"为所有 UI 按钮添加点击音效" "把所有 Enemy 的 Speed 设为 3"），测量首次成功率，目标 ≥ 60%
- **如果失败**：初期只做"建议+预览"模式（Agent 给出修改方案，用户确认后执行），降低信任门槛
- **风险等级**：橙色

### V4: Agent 是否比手动操作更快？
- **假设**："一句话完成任务" 比 "手动操作" 更高效
- **置信度**：高（85%）
- **判断依据**：即使 Agent 有 20% 失败率需要重试，整体耗时仍远低于手动
- **验证实验**：对比实验——5 个任务 × 10 人，Agent 组 vs 手动组，记录总耗时 + 错误率
- **风险等级**：黄色

## 2. Usability —— 可用性假设

### U1: 自然语言是否足以精确描述游戏开发意图？
- **假设**：用户可以用自然语言清楚地告诉 Agent 他们想要什么
- **置信度**：中（60%）
- **判断依据**："给角色加一个酷炫的攻击技能"——"酷炫"对 Agent 不可操作。用户需要学会说"生成一个持续时间 0.5s 的粒子特效，颜色红橙渐变，播放 slash 音效"
- **验证实验**：给 5 位非技术游戏策划开放 Agent，观察他们如何描述需求，记录需要 Agent 追问澄清的次数
- **如果失败**：建立"意图引导模板"——Agent 主动反问："你说的酷炫是指：A) 大量粒子 B) 屏幕震动 C) 慢镜头？"，降低描述门槛
- **风险等级**：橙色

### U2: 工具执行进度的可视化是否清晰？
- **假设**：Pipeline 执行面板（进度条+日志）对开发者足够了
- **置信度**：中（65%）
- **判断依据**：AI 3D Pipeline 可能跑 30s+，用户不知道 Agent 在干嘛就会焦虑
- **验证实验**：原型测试——让用户观察一个 30s 的 Pipeline 执行，事后问"你知道刚才发生了哪些步骤吗？"
- **如果失败**：增加步骤级可视化（每个工具的输出预览——如 TRELLIS 生成后显示 3D 预览图）
- **风险等级**：橙色

### U3: 桌面应用的安装和配置门槛是否可接受？
- **假设**：独立开发者愿意花 10 分钟安装配置一个桌面应用
- **置信度**：中高（70%）
- **判断依据**：参考 Blender/Unity Hub 的安装体验
- **验证实验**：给 5 个开发者安装包 + 文档，记录"下载 → 首次成功调用 Agent"的总时间
- **风险等级**：黄色

### U4: 多引擎切换的 UX 是否自然？
- **假设**：用户在 Unity 和 Unreal 间切换时，不需要重新学习 Harness
- **置信度**：中（60%）
- **判断依据**：引擎差异大，同一操作（如"创建空 GameObject"）在不同引擎中概念不同
- **验证实验**：让 Unity 用户切换到 Unreal 项目执行 3 个相同意图的任务，记录困惑点
- **风险等级**：橙色

## 3. Viability —— 商业可行性

### B1: 独立开发者是否愿意付费？付费多少？
- **假设**：独立开发者愿意为 Harness 付费
- **置信度**：中低（45%）
- **判断依据**：独立游戏开发者群体预算极低，竞品（Cursor $20/月、GitHub Copilot $10/月）价格锚点低
- **验证实验**：Landing Page + 预购意向测试——"你会为这个产品付费吗？A) 不会 B) $5/月 C) $10/月 D) $20/月 E) $50+"，目标 B+C+D ≥ 30%
- **如果失败**：开源 + 托管服务（免费桌面端 + 付费云端 GPU 跑 AI 模型）或转向 B2B（为中型工作室提供私有部署）
- **风险等级**：橙色

### B2: AI 模型的 API 成本是否可控？
- **假设**：正常使用下，每个开发者每月的 LLM API 成本可控制在 $20 以内
- **置信度**：中（55%）
- **判断依据**：游戏开发任务复杂度高，一个任务可能消耗 10K+ tokens；3D Pipeline 推理还需 GPU 资源
- **验证实验**：模拟 100 个典型任务，统计平均 Token 消耗，计算月成本（假设日活 2h）
- **如果失败**：强化本地 LLM 支持、模型路由（简单任务用小模型）、Pipeline 只调用开源模型本地推理
- **风险等级**：橙色

### B3: 平台方（Unity/Epic）是否会封堵或自研替代？
- **假设**：引擎 Editor API 不会被故意封堵
- **置信度**：中（50%）
- **判断依据**：Unity Muse 已推出、Epic 也有 AI 布局；如果他们自研类似功能，可能限制第三方接入
- **如果失败**：优先级 1 是确保核心技术 Harness Framework 不依赖特定引擎——即使 Unity 封堵，Agent 能力可迁移到 Godot 或自研引擎
- **风险等级**：黄色

## 4. Feasibility —— 技术可行性

### F1: 引擎 Editor API 能否被稳定地外部调用？【红线】

- **假设**：Unreal Engine 的 Editor Plugin API（Editor Subsystem、Remote Control API、Commandlet 等）足够支持外部程序通过 IPC 操作运行中的编辑器
- **置信度**：中（55%）
- **判断依据**：源码只读权限意味着可以深入理解引擎内部 API 和扩展点，但**不能修改引擎源码**。仍需依赖官方提供的 Editor Plugin 机制。优势在于能更准确地找到最佳扩展点、理解内部行为、编写更可靠的 Plugin；劣势在于无法绕过引擎层面的限制（如编辑器主循环不能被我方代码直接嵌入 IPC Server）
- **验证实验（最高优先级）**：写一个最简 POC——在 Unreal Editor 中通过 Editor Subsystem 启动 IPC Server，从外部程序发送"创建一个 StaticMeshActor 在 (0,0,100)"的命令，记录延迟和稳定性
- **如果失败**：回退到"生成脚本/资源 → 用户手动 Apply"模式
- **风险等级**：红线 🔴——引擎 IPC 是所有引擎操作工具的基础，失败则整个"操作引擎"功能降级

### F2: AI 3D 模型（Python 生态）与 Harness Core 的桥接成本？

- **假设**：通过 IPC（具体方案待选型：gRPC/Named Pipe/SharedMemory 等）可以高效桥接 Core ↔ Python AI 进程
- **置信度**：中高（70%）
- **判断依据**：成熟方案存在，但 3D 模型数据（GLB 几十 MB）的传输效率需要验证
- **验证实验**：POC——Core 发请求给 Python TRELLIS 进程，Python 生成 GLB，传回加载预览，测量总延迟 + 内存占用
- **风险等级**：橙色

### F3: GUI 框架选型是否合理？

- **假设**：存在能满足"类 VS Code 的 Agent 聊天界面"需求的 GUI 框架（富文本 + 流式渲染 + 插件管理 UX + 跨平台）
- **置信度**：中（60%）
- **判断依据**：候选方向包括原生 GUI 框架、Web 前端壳等，各有优劣。选型标准：开发效率、跨平台支持、富文本和代码高亮渲染能力、社区生态
- **验证实验**：用 1-2 个候选框架各写一个 Chat 面板原型，包含"用户消息 + Agent Markdown 回复 + Tool Call 卡片"，对比开发效率和效果
- **如果失败**：混合方案——核心服务用系统级语言，壳用 Web 前端
- **风险等级**：橙色

### F4: 多 Tool 并行执行的并发模型复杂度
- **假设**：Harness Execution Engine 可以安全地并行执行多个 Tool（如同时调用 TRELLIS 和 MoMask）
- **置信度**：中高（75%）
- **判断依据**：Pipeline DAG 是明确的——无依赖的工具可并行；但共享资源（文件系统、GPU 显存、引擎状态）的竞态条件需仔细处理
- **验证实验**：设计并行执行测试用例——10 个 Tool 并行执行，其中 3 对有资源竞争，验证死锁/活锁/资源争用
- **风险等级**：橙色

### F5: 上下文窗口能否装下典型游戏项目的上下文？
- **假设**：一个典型 Unity 项目的关键上下文（文件树、关键脚本、场景结构摘要）可以在 64K tokens 内描述
- **置信度**：中（55%）
- **判断依据**：中型 Unity 项目可能有 500+ 脚本、100+ 场景，全部塞入不可行；需要智能上下文检索（类似 Claude Code 的 agent 上下文压缩）
- **验证实验**：用 3 个真实独立游戏项目，提取 Agent 需要的"最小上下文"，测量 Token 数
- **风险等级**：橙色

### F6: 跨平台（Win/Mac/Linux）的工程成本

- **假设**：核心逻辑（非 GUI 部分）可以做到跨平台；GUI 的跨平台成本取决于选型结果
- **置信度**：中（60%）
- **判断依据**：系统级语言本身跨平台，但 Unreal Editor 仅 Win/Mac/Linux、AI 模型（CUDA 依赖）限制实际可达性
- **验证实验**：Phase 1 只做 Windows，Phase 2 评估 Mac/Linux 移植成本
- **风险等级**：黄色

### F7: 去中心化插件市场的技术实现复杂度

- **假设**："插件索引文件 + 外部托管" 的模式可以通过简单的 HTTP 下载 + 校验实现
- **置信度**：中高（75%）
- **判断依据**：VS Code Extension Marketplace、Homebrew 都是类似模式，技术上成熟；但需要处理版本兼容（插件 ↔ Harness Core API 版本）、依赖解析（插件 A 依赖插件 B）、增量更新
- **验证实验**：实现一个最小插件索引服务 + Harness 内插件安装流程（从 GitHub Release 下载 → 解压 → 加载），验证全流程可行性
- **风险等级**：橙色

### F8: 第一方插件（LLM Provider / MCP / AI 服务）的性能开销

- **假设**：将 LLM Provider、MCP Server 等核心功能以插件形式实现，不会引入不可接受的性能开销
- **置信度**：中（65%）
- **判断依据**：插件加载边界清晰（进程内 .dll/.so），调用开销可忽略；但如果某些 Provider 需要独立进程（如 Python 桥接），开销主要来自 IPC 延迟
- **验证实验**：对比"OpenAI Client 硬编码在 Core 中"vs"作为插件动态加载"的调用延迟差异
- **风险等级**：黄色

### F6: 跨平台（Win/Mac/Linux）的工程成本

- **假设**：核心逻辑（非 GUI 部分）可以做到跨平台；GUI 的跨平台成本取决于选型结果
- **置信度**：中（60%）
- **判断依据**：系统级语言本身跨平台，但 Unreal Editor 仅 Win/Mac/Linux、AI 模型（CUDA 依赖）限制实际可达性
- **验证实验**：Phase 1 只做 Windows，Phase 2 评估 Mac/Linux 移植成本
- **风险等级**：黄色

### F9: MCP 生态依赖风险

- **假设**：社区的 Unreal-MCP / Unity-MCP / Godot-MCP Server 会持续维护，API 稳定
- **置信度**：中（55%）
- **判断依据**：Epic 已将 MCP 内置到 UE 5.8——官方支持保证 Unreal MCP 的长期可用性；但社区 MCP Server（IvanMurzak、ultimate-unreal-engine-mcp 等）的维护依赖个人/小团队。如果某个 MCP Server 停止维护，Harness 的工具集可用性会受损
- **验证实验**：评估 Epic 官方 Unreal MCP 的工具覆盖率——是否已覆盖 Harness 需要的 80%+ 操作？跟踪社区 MCP Server 的 GitHub 活跃度（commit 频率、issue 响应时间）
- **如果失败**：对关键缺失工具做自建 MCP Server（符合 MCP 协议，社区也可复用），而非回到自建 IPC 路线
- **风险等级**：橙色

### F10: 多 Agent 架构的复杂度

- **假设**：Planner + Coder + Asset + Reviewer 的多 Agent 分工在工程上可行，不会过度增加开发复杂度
- **置信度**：中低（45%）
- **判断依据**：学术论文（AutoUE/OpenGame）验证了多 Agent 的有效性，但都是在受控实验条件下。生产环境中多 Agent 的上下文管理、错误传播、任务拆解准确性都是未验证的
- **验证实验**：Phase 1 先做单 Agent（验证核心闭环），Phase 2 逐步引入多 Agent，对比单 Agent vs 多 Agent 在典型任务上的成功率
- **如果失败**：回退到单 Agent + 精心设计的 System Prompt 和工具 Schema——大多数同类产品也是单 Agent
- **风险等级**：橙色

### F11: Sandbox 隔离执行的性能开销

- **假设**：文件系统级别的隔离（类似 git worktree）不会显著影响开发体验（< 5s 额外延迟）
- **置信度**：中（60%）
- **判断依据**：git worktree 操作通常 < 1s（对大项目可能是 3-5s）；Unreal 项目动辄几十 GB，Sandbox 初始化和合并的性能需要验证
- **验证实验**：在 3 个不同规模的 Unreal 项目上测试 Sandbox 创建/合并延迟
- **风险等级**：黄色

## 5. Ethics —— 伦理风险

### E1: AI 生成的 3D 资产是否存在版权/合规风险？
- **假设**：使用 MIT/Apache 2.0 许可的开源模型 + 用户提供参考图，版权风险可控
- **置信度**：中（60%）
- **判断依据**：AI 训练数据来源复杂；TRELLIS (MIT) 合法，但模型训练集是否包含受版权保护数据仍存争议；用户上传的参考图版权归属也需要免责
- **验证实验**：咨询法律顾问，明确 User Terms——"Harness 不拥有任何版权，AI 产出风险的最终责任在用户"
- **风险等级**：橙色

## 6. Go-to-Market —— 市场进入

### G1: 如何触达独立游戏开发者？【红线】
- **假设**：通过 Reddit / YouTube / Bilibili / Discord 社区可以有效触达目标用户
- **置信度**：低（35%）
- **判断依据**：独立开发者分散在无数社区中，没有一个"所有独立开发者都会去的地方"；触达成本可能很高
- **验证实验（高优先级）**：在 r/gamedev、r/IndieDev、Unity 中文社区各发一篇 Harness 的概念介绍帖，统计 1 周内的点赞/评论/Star 和转化率（Landing Page 访问量）
- **如果失败**：转向 Game Jam 赞助（送 Harness Pro 许可给参赛者）或与游戏开发 KOL 合作
- **风险等级**：红线 🔴

### G2: 从 Unreal 生态切入是否是最优选择？

- **假设**：从 Unreal 生态切入最有利——拥有源码权限，技术天花板最高
- **置信度**：中高（70%）
- **判断依据**：Unreal 在 3A/中大型项目份额大，独立游戏市场 Unity 份额更高；但源码权限 + C++ 原生支持是不可替代的优势
- **验证实验**：在 Unreal 社区（Forums/Reddit/Discord）调研"你最希望 Unreal 自动化什么？"，统计需求分布
- **风险等级**：橙色

### G3: 是否有清晰的病毒传播路径？
- **假设**：开发者用 Harness 做出好东西后会主动分享
- **置信度**：中低（40%）
- **判断依据**：参考 Cursor 的传播路径——"Showcase"（晒 Agent 生成的炫酷效果）是最自然的病毒传播
- **验证实验**：MVP 阶段设计"一键导出 Showcase 视频"功能，内置 watermark，降低分享门槛
- **风险等级**：橙色

### G4: 是否需要在 App Store / Steam 上架？
- **假设**：独立开发者会从官网/GitHub 下载桌面软件
- **置信度**：中（60%）
- **判断依据**：开发者习惯从 GitHub/官网下载工具；但 Steam 上架（类似 Blender on Steam）能获得额外流量
- **风险等级**：橙色

## 7. Strategy & Objectives —— 战略风险

### S1: 如果 Unity/Epic 几个月后发布同类 Agent 产品怎么办？
- **假设**：我们在引擎无关性 + 开源模型可控性上有 12 个月窗口期
- **置信度**：中（50%）
- **判断依据**：Unity Muse 已发布但功能有限，Epic 尚未公告 Agent 产品；大厂动作慢，12 个月窗口合理
- **应对策略**：差异化竞争——做大厂不愿做的（开源、多引擎、本地优先），快速占领 niche 市场建立品牌
- **风险等级**：橙色

### S2: 先做深度（Unreal 所有功能）还是广度（多引擎）？

- **假设**：先在 Unreal 上做到"独立开发者觉得有用"，再横向扩展 Unity/Godot
- **置信度**：中高（75%）
- **判断依据**：多引擎同时做会稀释开发资源；Unreal 有源码权限，深度集成可行性强
- **风险等级**：黄色

### S3: 是否应该开源核心框架？
- **假设**：开源 Harness Core + 收费增值服务（云端 GPU、高级 Pipeline、企业支持）是最优模式
- **置信度**：中（50%）
- **判断依据**：开源促进社区贡献（工具插件）、建立信任（用户可审查代码）；但可能被大厂 Fork 后集成到自家产品
- **验证实验**：研究 Cursor / Blender / Godot 的开源商业模式，评估对 Harness 的适用性
- **风险等级**：橙色

### S4: AI 3D 管线是否应该做自研模型还是只用第三方？
- **假设**：Phase 1-2 只用开源模型封装，不碰模型训练
- **置信度**：高（85%）
- **判断依据**：模型训练成本极高（数据、算力、人才），开源模型进步速度已够快
- **风险等级**：黄色（方向正确）

## 8. Team —— 团队风险

### T1: C++ 开发者的招聘/培养是否困难？
- **假设**：能找到足够的 C++ 开发者（特别是 Qt + 游戏引擎经验的）
- **置信度**：中（55%）
- **判断依据**：C++ 游戏开发者相对多（Unreal 生态），但愿意做工具而非游戏的人才少；Qt 开发者就更少
- **风险等级**：橙色

### T2: 一个人能否扛起 Phase 1 MVP？
- **假设**：1 个全栈 C++ 开发者可以在 3 个月内交付 Phase 1
- **置信度**：中（50%）
- **判断依据**：Phase 1 范围包括 Harness Core + Unity Adapter + LLM Integration + Qt UI + 2 个 AI 工具，工作量偏大
- **验证实验**：拆解 Phase 1 到人天级别的 WBS，评估实际工作量
- **如果失败**：砍 Phase 1 范围——只做 CLI 版本（无 Qt UI），或只做 3D Pipeline 不做引擎操作
- **风险等级**：橙色

### T3: 是否需要 AI/ML 专长的团队成员？
- **假设**：Phase 1-2 封装开源模型不需要 ML 专长
- **置信度**：中高（70%）
- **判断依据**：TRELLIS/MoMask 有现成的 inference 脚本，封装为 subprocess 调用不需要 ML 知识；但遇到模型 bug 或需要 Fine-tune 时就需要了
- **风险等级**：黄色

### T4: 项目是否会因为技术债务积累而减速？
- **假设**：C++ 项目如果一开始架构良好，技术债务可控
- **置信度**：中低（45%）
- **判断依据**：C++ 缺少标准包管理器、反射、模块系统；容易写出紧耦合代码；尤其是 Plugin System 和跨进程通信的设计需要慎重
- **应对策略**：Phase 1 花 20% 时间做架构设计评审；核心接口（Tool Registry、Execution Engine）用纯虚接口 + 单元测试锁死
- **风险等级**：黄色
